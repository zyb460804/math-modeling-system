# Model Contract Template（模型合同模板）

> **用途**：在开始任何建模分析之前，必须先建立 Model Contract，系统性规划分析方向。
> **来源**：math-modeling-skill/references/roles/建模手/references/前置合同.md
> **版本**：v1.0

---

## 1. 一句话核心结论（Core Conclusion）

用一句话写出本题必须回答的核心问题。这是整个建模工作的出发点，所有后续模型选择和分析都围绕这句话展开。

**要求**：
- 必须包含：研究对象 + 约束条件 + 目标输出
- 不得包含具体模型名称（模型是手段，不是目标）
- 长度：一句话，不超过 40 字

**示例**：
> "在给定资源约束下，最大化物流配送效率并给出最优路线方案"
> "基于历史数据，预测某地区未来一年的空气质量变化趋势"
> "建立多因素评价模型，对 N 个城市进行综合排名"

---

## 2. 证据链与防冗余原则（Evidence Chain）

将核心结论拆解为若干需要论证的子问题，每个选用的模型负责回答其中一个子问题。

### 防冗余原则

**核心规则**：如果去掉某个模型后，核心结论仍能从其他模型的求解结果中完整推导出来，则该模型是冗余的。

每个模型必须承载**独特且不可替代**的分析维度，模型之间应形成互补证据链而非重复验证。

**自检方法**：对表格中的每一行，尝试遮盖该行后问自己："剩余模型能否完整支撑核心结论？" 如果能，该行是冗余的。

### 子问题-模型映射表

| 子问题 | 选用模型 | 该模型承担的证据角色（独特且不可替代） | 备选方案 |
|--------|---------|--------------------------------------|---------|
| 子问题 A：[描述] | [模型 X] | [它唯一能证明的结论] | [模型 Y] |
| 子问题 B：[描述] | [模型 Z] | [它唯一能证明的结论] | [模型 W] |
| 子问题 C：[描述] | [模型 V] | [它唯一能证明的结论] | [模型 U] |

**填写要求**：
- 证据角色列必须写清楚"这个模型证明了什么其他模型无法证明的"
- 备选方案必须是真实可运行的替代模型，而非占位符
- 子问题数量建议 2-4 个（对应竞赛题的小问数）

---

## 3. 候选评估 + 备选方案（Candidate Evaluation）

对每个子问题，评审候选方案并记录决策理由。此表供 G2.5 人类决策门禁使用。

### 评审矩阵

| 评审项 | 子问题 A | 子问题 B | 子问题 C |
|--------|---------|---------|---------|
| **候选方案** | 列出 2-3 个候选模型 | 同左 | 同左 |
| **选择理由** | 数据适配性 / 复杂度 / 可解释性 | 同左 | 同左 |
| **潜在风险** | 模型局限性、数据要求、计算成本 | 同左 | 同左 |
| **备选方案** | 首选失败时的替代方案 | 同左 | 同左 |
| **切换触发条件** | 什么条件下启用备选方案 | 同左 | 同左 |

### PoC 验证要求

每个候选方案必须通过 PoC 验证门禁（Gate G2）：
- PoC 代码 <= 30 行
- 必须产出一个可行性数字（feasibility number）
- 使用真实清洗后数据（非模拟数据）
- 失败的 PoC 标记 `[REJECTED]` 并归档

## 4. 下游交付规格（Downstream Delivery Specs）

Model Contract 是建模手对下游（编程手、论文手）的承诺。以下表格定义了每项交付物的接收方和规格要求。

### 对编程手的交付

| 交付物 | 格式要求 | 位置 |
|--------|---------|------|
| 模型公式与推导 | 精确的数学表达式、参数含义、取值范围 | `methods/Qx/qx_final_method_explanation.md` |
| 算法步骤与伪代码 | 详细的求解流程、输入输出格式、边界条件 | 同上 |
| 可视化需求清单 | 图表类型、数量、核心信息、Figure Contract | `methods/Qx/qx_figure_table_plan.md` |
| 评估指标定义 | 指标名称、计算公式、合理范围 | `planning/symbol_table.md` |

### 对论文手的交付

| 交付物 | 格式要求 | 位置 |
|--------|---------|------|
| 模型选择依据 | 理论文献支撑、对比分析理由 | `results/Qx/reports/qx_solution_package_for_writer.md` |
| 参考文献 | 完整引用格式（论文名称、作者、年份、来源） | `paper/refs.bib` |
| 术语表 | 中英文术语对照、符号定义 | `planning/symbol_table.md` |
| 结果解读 | 每个数值结果 >= 3 个讨论维度 | `results/Qx/reports/qx_final_result_analysis.md` |

## 5. 填写示例（Example）

以下是一个完整的 Model Contract 示例，以"城市空气质量综合评价与预测"为例。

```markdown
## Model Contract — 202X 国赛 X 题

### 核心结论
基于多源监测数据，建立城市空气质量综合评价体系并预测未来 6 个月的变化趋势。

### 子问题拆解与模型映射

| 子问题 | 选用模型 | 证据角色 | 备选方案 |
|--------|---------|---------|---------|
| Q1：综合评价 | 熵权-TOPSIS | 量化 6 城市空气质量排名，消除主观权重 | AHP-TOPSIS、CRITIC-TOPSIS |
| Q2：趋势预测 | ARIMA | 基于时序特征的定量预测，给出置信区间 | LSTM、Prophet |
| Q3：因素分析 | 灰色关联度 | 识别影响空气质量的关键因素及排序 | 皮尔逊相关、随机森林特征重要性 |

### 候选评估

| 评审项 | Q1 综合评价 | Q2 趋势预测 | Q3 因素分析 |
|--------|-----------|-----------|-----------|
| 候选方案 | 熵权-TOPSIS / AHP / CRITIC | ARIMA / LSTM / Prophet | 灰色关联 / 皮尔逊 / RF |
| 选择理由 | 数据量适中，熵权客观性强 | 数据为月度时序，ARIMA 可解释性好 | 数据含灰色特征，关联度适配 |
| 潜在风险 | 对异常值敏感，需预处理 | 非线性趋势可能拟合不足 | 样本量小，关联度可能不稳定 |
| 备选方案 | AHP-TOPSIS（引入专家权重） | LSTM（捕捉非线性） | 随机森林（数据量足够时） |
| 切换条件 | 熵权结果与常识严重不符 | ARIMA 残差不满足白噪声 | 灰色关联排序与领域知识冲突 |

### 对编程手
- Q1：需实现熵权计算 + TOPSIS 排序，输出排名表 + 灵敏度分析图
- Q2：需实现 ARIMA(p,d,q) 自动定阶 + 预测，输出预测曲线 + 置信区间图
- Q3：需实现灰色关联度计算，输出关联度排序图

### 对论文手
- Q1：需引用 3+ 篇熵权-TOPSIS 应用文献，说明为何不选 AHP
- Q2：需讨论 ARIMA 的适用条件和局限性，引用 Box-Jenkins 方法论
- Q3：需说明灰色关联度与传统相关分析的区别，引用邓聚龙原著
```

## 6. 质量自检清单

在完成 Model Contract 后，逐项检查：

- [ ] 核心结论是否包含研究对象 + 约束 + 目标？
- [ ] 核心结论是否不含具体模型名称？
- [ ] 每个子问题的证据角色是否独特且不可替代？
- [ ] 遮盖任意一行后，剩余模型能否完整支撑核心结论？（防冗余）
- [ ] 每个候选方案是否有真实可运行的备选方案？
- [ ] 每个候选方案是否有 PoC 验证计划？
- [ ] 交付规格是否覆盖编程手和论文手的所有需求？
- [ ] 下游交付物的位置路径是否与 workspace 结构一致？
